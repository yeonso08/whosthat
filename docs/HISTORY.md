## 1-1. 명단·계정 채우기 경과

- **나는 솔로 1~33기 명단이 2026-08-21 에 다 들어갔다**(408명). 1~5기(초기 가명 체계)·25기(미경 대체자 불명)·32기(인원 자료 불일치)가 오래 비어 있다가 이때 채워졌다. 그래서 "명단 정리 중" 과 거기 딸린 noindex·sitemap 제외에 걸리는 기수가 지금은 없다 — 장치를 걷어낸 게 아니라 해당자가 없는 것이다. `lib/seo.ts` 의 `isIndexable` 은 그대로 살아 있고, 새 기수를 골격만 먼저 넣으면 다시 작동한다.

## 2. 정리·재디자인

**정리 한 번 돌았다**(2026-08-25). 죽은 CSS 토큰(`--sidebar-*`·`--chart-*`·`create-next-app` 잔재)과 안 쓰는 shadcn 파일(`textarea`·`separator`)을 걷어내고, 중복을 다음 다섯 곳으로 모았다: 공유 카드(`lib/og.tsx`), 브랜드 타일(`BrandTile`), 정책 페이지 껍데기(`PolicyPage`)와 그 metadata(`policyMetadata`), 브랜드 이름(`BrandName`), 사이트 집계(`getTotals`). 경로 리터럴은 `links.ts` 로, 절대 URL 은 `absoluteUrl` 로 모았고, `contactMailto` 를 `links.ts` 에서 `site.ts` 로 옮겨 **클라이언트 번들에서 `site.ts` 를 뺐다**(언어 전환 버튼이 `links.ts` 를 타고 끌고 들어오던 것이다). 화면 동작은 그대로고 빌드도 117 페이지 그대로다.

**화면을 통째로 다시 짰다**(2026-08-31). "딱딱하고 투박하다" 는 지적이 출발점이었고, 시안 D 의 방향은 그대로 두고 면(그림자)·활자(무게 900→700)·움직임(`lift`/`press`)·구성(홈 가운데 정렬, 목록의 `ListCard`, 정사각 출연진 카드)만 바꿨다 — 근거는 `CLAUDE.md` 의 "면·활자·움직임" 절. 상단 바의 프로그램 링크도 이때 뺐다(프로그램이 계속 늘어서 어느 개수에서 반드시 넘친다).

**처리방침·삭제 창구는 프로그램이 늘면 같이 손본다.** 나는 솔로만 있던 시절의 문구가 `가명`·`기수와 가명(예: 28기 영숙)` 을 전제하고 있었다 — 솔로지옥은 실명으로 나오는 프로그램이라 그대로 두면 처리방침이 사실과 다른 말을 한다. 2026-08-31 에 `privacy.cast1` 과 `/takedown` 의 요청 예시·메일 제목을 "방송에서 불린 이름" 쪽으로 고치고 `effectiveDate` 를 함께 옮겼다.

## 3. 검색엔진 등록 (2026-08-24)

검색엔진 등록을 커스텀 도메인 연결 뒤로 미뤄 둔 이유는 검증과 색인이 **호스트네임 단위로** 쌓이기 때문이었다 — `.vercel.app` 으로 먼저 등록했으면 도메인을 옮길 때 검증·sitemap 제출·색인을 통째로 다시 했을 것이다. 한국어 쿼리로 안 뜨던 것도 온페이지 문제가 아니라 단순 미등록이었다(`site:www.nukko.net` 으로 확인했었다).

커스텀 도메인은 2026-08-24 에 연결했고, 절차는 `CLAUDE.md` 의 "커스텀 도메인을 연결할 때"에 있다. 요점은 **코드를 고칠 게 없다는 것** — `lib/site.ts` 한 곳이 도메인을 정한다.

다만 **"Primary 도메인 지정" 같은 설정은 Vercel 에 없다.** 자동값(`VERCEL_PROJECT_PRODUCTION_URL`)이 "가장 짧은 커스텀 도메인"을 고르는 탓에 리다이렉트 전용인 apex 가 뽑히므로, `NEXT_PUBLIC_SITE_URL` 로 못박는 게 맞다. sitemap 의 `<loc>` 은 프로덕션에서 확인했다(전부 `https://www.nukko.net`).

**남은 건 색인을 기다리는 것뿐이다.** 등록·sitemap 제출은 운영이 끝냈고 이제부터는 각 엔진의 크롤링 속도에 달렸다 — 며칠에서 몇 주 걸릴 수 있다. `site:www.nukko.net` 으로 가끔 진행 상황을 확인하면 된다.

**대신 sitemap `lastmod` 버그를 찾아 고쳤다.** 138줄 중 108줄에 `lastmod` 가 없었다. 출연자 `lastVerified` 중 최신을 쓰면서 빠진 값을 `undefined` 로만 걸렀는데, DB 로 옮긴 뒤(9/7) API 는 빠진 값을 `null` 로 준다 — 못 찾은 사람이 한 명이라도 있으면 `null` 이 정렬 맨 뒤로 가서 날짜가 통째로 사라졌다. 날짜가 붙은 30줄도 계정 확인일(8/21·9/2)이라 9/22 의 소개 문단 같은 내용 변경을 못 봤다. 이제 `seasons.updated_at`(기수·출연자·소개 문단 어느 표가 바뀌어도 DB 트리거가 올린다)을 쓰고, 홈·프로그램 화면은 그 기수들 중 가장 최근 값이다. 기존 값은 백업 이력으로 채웠다 — 전 기수 9/22, 33·34기 10/11. `lastmod` 는 다시 읽어 갈 때가 됐는지의 신호라 크롤링을 안 한 원인이라고는 할 수 없다(nukko-admin-api#8, whosthat#81).

**구글 노출을 로그인한 브라우저로 확인하지 말 것.** Search Console 소유자 계정으로 로그인된 브라우저는 검색 결과가 개인화돼서, 일반 방문자에게 안 나오는 페이지가 나온다. 조사 중에 그걸 근거로 "나온다" 고 잘못 판단했다. 노출은 Search Console 실적으로 본다.

## 7. 네이버 서치어드바이저 확인·수집 요청 (2026-10-15)

**계기.** 10/14 하루 방문자 50명이 전부 네이버에서 왔고, 네이버 검색 상단 AI 브리핑이 누꼬를 출처로 인용하고 있었다(10기 검색에서 누꼬·솔로딕 두 곳). 다만 `나는솔로 33기 인스타` 는 AI 브리핑이 뜨는데 `나는솔로 33기 영수 인스타` 는 안 떴고, 기수에 따라 브리핑에 나오는 곳과 안 나오는 곳이 갈렸다.

**서치어드바이저 실적(최근 30일).** 클릭 210·노출 약 1.7만, 10/1 무렵부터 급증했다. 노출이 잡힌 기수 페이지는 한국어 2·3·8·10·16·19·24·25기 **여덟 개뿐**이고, 나머지는 홈과 영어 25기가 한 자릿수였다. 웹 페이지 수집 요청은 그때까지 한 번도 안 했고 sitemap 은 8/31 에 낸 것뿐이었다.

**인물 검색어는 이미 된다.** `2기 영숙 인스타`·`8기 정숙 인스타`·`나는솔로 2기 영수 인스타` 로 클릭이 났다. 그러니 `33기 영수` 가 안 뜨는 건 페이지 구조가 아니라 **33기 페이지가 네이버에 안 잡혀서**다 — 기수마다 AI 브리핑 노출이 갈리는 것도 같은 이유로 본다(10기는 노출 2위 페이지다). 검색어마다 AI 브리핑을 띄울지는 네이버가 정한다. 이 근거로 **출연자별 페이지를 따로 만드는 안은 접었다**(기수 페이지가 사람 이름으로도 걸리는데 같은 내용을 얇은 페이지로 쪼갤 이유가 없다).

**노출이 없던 기수 30개를 수집 요청했다**(요청 → 웹 페이지 수집, 전부 `/ko/`): 나는 솔로 1·4·5·6·7·9·11~15·17·18·20~23·26~33기, 솔로지옥 시즌 1~5. 거절 없이 다 들어갔다. 34기는 계정이 0개라 뺐다가 2026-10-22 에 따로 넣었고(직업·나이와 지난 기수 판이 붙은 뒤, 방송 다음 날 34기 유입이 몰린 때), 영어·일본어는 네이버 이용자가 거의 한국어로 검색하고 hreflang 으로 이어져 있어 뺐다.

**노출은 많은데 클릭이 적은 검색어**: `나는솔로 25기` 1,511회 0.5%, `나는솔로 16기 출연진` 845회 0.5%. 손대지 않고 기록만 해 뒀다.

네이버는 FAQ 구조화 데이터 노출을 7/8 에 끝냈다 — FAQ 페이지의 `FAQPage` JSON-LD 가 네이버에서 따로 보이길 기대할 것은 없다.

## 8. 검색 설명에 출연자·직업, 직업 번역 (2026-10-19)

**계기.** 네이버에서 `나는솔로 25기` 가 노출 1,511회에 클릭률 0.5% 였다(§7). 순위가 아니라 검색 결과 한 칸이 안 눌리는 문제로 봤다 — 기수로 검색한 사람은 누가 나왔는지가 먼저 궁금한데, 설명이 사이트 소개("확인된 것만 모아 뒀고…")뿐이었다.

**기수 상세의 검색 설명을 바꿨다**(whosthat#83). `출연진 12명, 인스타 6명 확인 — 광수(39·이비인후과 의사), …` 다. 인스타 확인 수를 앞에 둔 건 모바일 검색 결과가 뒤를 자르면 누꼬만 주는 정보가 먼저 사라지기 때문이고, 데이터가 남·여 순이라 4명을 번갈아 고른다. 직업이 없는 기수(1~19기·33·34기)는 예전 문구다.

**직업 번역을 붙였다.** 그전엔 직업이 한국어 한 칸뿐이라 영어·일본어 카드에 한국어가 나갔고, 검색 설명도 영어·일본어에서는 예전 문구로 떨어뜨려야 했다. 이름처럼 짝 표가 아니라 출연자 행의 컬럼(`occupation_en`·`occupation_ja`)으로 뒀다 — 164명에 161가지라 거의 사람마다 한 줄이다(nukko-admin-api#9, nukko-admin#7, whosthat#85). 첫 초안 229개는 스크립트로 한 번에 넣었다(nukko-admin-api#10). 가린 회사 이름은 번역에서도 가렸다(`S반도체` → `"S" semiconductor company` / `S半導体`).

**효과는 아직 모른다.** 배포 2~3주 뒤 서치어드바이저에서 `나는솔로 25기` 클릭률을 0.5% 와 비교한다. 16기는 직업이 비어 이번 변경이 안 걸려 대조군으로 두었다(PROGRESS "네이버 수집 확인"). **2026-10-23 에 접었다** — 그날 16기 소개 문단에 한 줄을 더하고 상철 계정을 비공개 전환으로 바꾸면서 본문이 바뀌었다(검색 결과의 제목·설명은 그대로였다). 깨끗한 대조군이 아니게 되어 사용자가 비교군 자체를 두지 않기로 했다. 이제 16기 직업·나이도 채워도 된다.

## 11. IndexNow · Bing 색인 점검 (2026-11-03)

**계기는 "DuckDuckGo 에도 색인되게 하고 싶다" 였다.** DuckDuckGo 는 sitemap 을 받는 창구가 없다 — 결과를 Bing 색인에서 받아 쓴다. `site:nukko.net` 결과가 두 엔진에서 순서까지 똑같은 것으로 확인했다. 그래서 할 일은 DuckDuckGo 가 아니라 Bing 쪽이었고, Bing 은 2026-08-24 에 이미 등록돼 있었다(§3).

**Bing 상태(Webmaster Tools, 2026-11-03)** — sitemap 138줄 전부 발견·오류 0·마지막 크롤링 10-29. Site Explorer 기준 **색인 92 · 오류 0 · 경고 1 · 제외 17**, 최근 6개월 노출 63·클릭 1. 경고는 루트 `/`(proxy 가 언어로 보내는 주소라 정상)다. 제외 17건은 목록을 열어 보지 않았다 — 옛 주소(308) 로 보인다. 공개 검색의 `site:` "약 51개" 는 추정치라 실제 색인 수와 다르다.

**IndexNow 를 붙였다**(#110, #111). 한 곳에 보내면 참여 엔진(Bing·네이버·Yandex·Seznam)이 나눠 갖는다. **구글은 안 받는다** — 구글은 지금처럼 sitemap 이다.
- 키 파일 `public/<키>.txt` + `scripts/indexnow.mjs` + `.github/workflows/indexnow.yml`(매시 17분, 수동 실행 가능).
- **배포에 매달지 않고 한 시간마다 라이브 sitemap 을 본다.** "사이트에 반영" 이 Deploy Hook 이라 GitHub 가 배포의 끝을 모르고, 빌드 중에 보내면 크롤러가 옛 화면을 받아 간다. 지난번 sitemap 을 Actions 캐시에 스냅숏으로 들고 다니며 `lastmod` 가 바뀐 주소와 빠진 주소만 보낸다. 바뀐 게 없으면 아무것도 안 보낸다.
- 첫 실행(수동)에서 138개를 보내 `202`(받음, 키 확인 대기)를 받았다.
- 한계: `lastmod` 가 없는 소개·FAQ·정책 페이지는 문구를 고쳐도 다시 안 보낸다(처음 한 번만 나갔다).

## 12. 기수마다 회차별 정리 (2026-11-05)

애드센스 3차 거절(10-28) 뒤 정한 "출연자 기록 아카이브" 개편의 첫 단계다. 기수 상세가 남의 사이트로 가는 링크 모음으로 읽히지 않게, 누꼬가 정리한 방송 기록을 페이지의 주인공으로 올린다.

**형식은 시안 세 번 만에 정했다.** 33기로 표·득표 막대·카드 속 한 줄(A/B/C)을 만들었다가 "게임 캐릭터 수치나 공략 같다" 로 반려, 첫날·마지막 날만 산문으로 쓴 글은 "뉴스 기사나 소설책" 이라 반려됐다. 통과한 건 나솔 정리 블로그 형식 — 방송 날짜마다 끊고 짧은 문단·인용·자기소개 상자·선택 결과 상자를 섞는다. 디테일에서 가명 원 배지(이름이 두 번 찍힘)와 `· 여자가 골랐습니다` 같은 꼬리표를 걷어냈다.

**만든 것** — 하루에 끝까지 갔다.
- DB 표 넷(`season_episodes`·`episode_blocks`·`pick_rounds`·`picks`)과 관리자 API(nukko-admin-api #17). 선택은 한 사람당 한 행, 커플은 저장하지 않고 최종 선택에서 서로 고른 짝으로 센다. 회차는 통째로 저장한다(PUT).
- 관리자 입력 화면(nukko-admin #9). 브라우저로 눌러 보다 "여자가 골랐습니다" 선택 목록에 다른 여자가 같이 나오는 버그를 잡았다 — 상대 목록은 늘 이성뿐이다.
- 누꼬 화면(#114·#116). 33기 시안을 데이터로 그리게 옮기고 mockup 을 지웠다. 커플 카드가 id 순이라 "영철과 정숙" 이 먼저 나와서 출연진 순서로 고쳤다.
- 초안 스크립트(nukko-admin-api #18 이후) — 가명으로 적은 JSON 을 API 와 같은 검사로 넣는다.

**채운 것: 16~34기 19개 기수**(nukko-admin-api #18~#36, 기수마다 PR 하나). 기수마다 기사를 회차별로 찾아 쓰고, 넣고, 로컬에서 그려 본 뒤 머지·반영했다. 배운 것:
- **회차 번호와 방송일을 먼저 못박는다.** 다음 기수 첫 방송에서 거꾸로 센 뒤 결방(설·추석·연말)을 기사로 확인했다. 실제로 결방은 하나도 없었고, 18기는 시작이 한 주 늦었다.
- **기사끼리 선택이 엇갈리면 데이트 장면과 맞물리는 쪽만 남긴다.** 서플의 한 종합 기사가 여러 기수 내용을 섞어 29기·23기 어느 쪽과도 안 맞았다 — 쓰지 않았다.
- **선택 상자에는 확인된 줄만** 넣고 나머지는 "확인하지 못했습니다". 표 수만 알고 누가 골랐는지 모르면 상자 없이 글로만 썼다.
- **뺀 것이 많다** — 논란·갈등·소문(16·23·28·31기가 특히 컸다), 자녀·이혼 사유·사별·재산·건강, 외모 평가, 방송 뒤 근황. 그래서 갈등 위주 기수는 중반 회차가 한 문단씩이다. 23기 정숙은 제작진 통편집이라 다루지 않았다.
- 반영 훅이 한 번 10초 안에 답하지 않아 에러가 났지만 빌드는 들어갔다(32기). 대기 수만 남았다가 다음 반영 때 정리됐다.

**이어서 10~15기 6개 기수**(2026-11-09~10, nukko-admin-api #38~#43). 15기 7 · 14기 8 · 13기 8 · 12기 8 · 11기 7 · 10기 10회차. 15기는 머지 뒤 두 군데를 바로잡았다 — 첫 데이트 문장에서 영숙이 귀엽다고 한 대상, 소개 문단의 회차 범위(100~106회). 이 무렵부터 기사가 눈에 띄게 줄어 중반 회차가 짧다.

**마지막으로 1~9기 9개 기수**(2026-11-11, nukko-admin-api #44~#52). 9기 8 · 8기 6 · 7기 6 · 6기 8 · 5기 6 · 4기 6 · 3기 5 · 2기 6 · 1기 7회차. 이걸로 나는 솔로 1~34기가 다 찼다. 그사이 걸린 것:

- 6기 최종 선택 문장이 "영숙이 아무도 안 골랐다" 로 읽혀 넣은 뒤 고쳤다(영숙은 영철을 골랐다). 이미 있는 날짜는 스크립트가 건너뛰어서, 그 회차만 API 의 `replace_episode` 와 같은 순서로 지우고 다시 채웠다. 이 뒤로는 최종 선택 문장을 넣기 전에 따로 읽었다.
- 1기 6회 "두 명만 남기기" 는 한 사람이 두 줄을 가져 선택 상자 검사(한 사람이 두 번 고를 수 없다)에 걸린다 — 글로 풀었다.
- 1기 마지막 회의 영철·영숙 웨딩 사진은 방송이 직접 공개한 장면이라 넣었다. 방송 뒤 근황은 넣지 않았다.

## 13. 나솔사계 추가 (2026-11-12)

세 번째 프로그램으로 "나는 SOLO, 그 후 사랑은 계속된다"(나솔사계, `i-am-solo-love-goes-on`)를 붙였다. 사용자가 정한 것 셋 — **단위는 솔로민박 번호**(기수 번호가 없는 프로그램이다), **최근 것부터**, **주소는 넷플릭스 표기로 알려진 `I'm SOLO, Love goes on`**(출처는 블로그 하나라 직접 확인 못 했다).

**걸린 것**

- **꽃 이름은 특집마다 다시 쓴다.** "나솔사계 국화 인스타" 로 찾으면 다른 특집의 국화가 나온다 — 13 국화(SRT 승무원)와 16 국화(항공 승무원 출신 아카데미 대표)가 실제로 다른 사람이었다. 기사·게시물 날짜와 특집을 맞춰 본다.

## 14. 계약결혼 추가 (2026-11-13)

네 번째 프로그램으로 남규홍 PD 의 결혼 관찰 예능 "계약결혼"(MBC every1·KBS joy, 월요일 22:30, 2026-09-28 시작)을 붙였다. 사용자가 정한 것 셋 — **단위는 `시즌 1` 하나**(이 프로그램은 기수·시즌 없이 "계약 부부" 만 있다), **이름은 방송대로 실명**(솔로지옥처럼, `name` 칸은 비운다), **주소는 공식 영어 제목 `contract-marriage`**.

**넣은 것** — 계약 부부 둘, 4명. 전원 나는 솔로·나솔사계 출신이다: 강정환(16기 상철)–정유진(28기 영숙, 시애틀), 최정현(32기 영수)–정민현(솔로민박 13 국화, 파주). 프로그램·문구 3개 언어·기수·출연자·이름 번역 3개(`정유진` 은 솔로지옥에 이미 있었다)는 일회성 스크립트(로컬 `.env` DB, 드라이런 → `--apply`), 소개 문단 3개 언어와 회차별 정리 1~7회는 nukko-admin-api #60.

- **이름**: 방송에서는 이름만 부른다(정환·유진·정현·민현). 성까지 붙은 이름은 기사 표기이고, 강정환은 1회에 "저는 강정환" 이라고 소개했다(MBC연예 9/28) — 기사 제목에 7곳이 쓴다.
- **회차별 정리**는 회차마다 방송 당일·다음 날 다음 뉴스 날짜 검색으로 기사 2~5건을 읽었다. 고르는 형식이 아니라 선택 상자가 없고 글·인용·자기소개만 있다. **처음엔 자녀·이혼·흡연·코골이·음주·외모·수입 이야기와 6~7회 카메라·일기장 장면을 뺐다가, 사용자가 "실제 결혼 이야기라 빼면 독자에게 진실되지 않다" 며 되살렸다**(회차를 지우고 다시 넣었다). 방송에 안 나온 것(16기 상철의 과거 논란 기사, 32기 영수의 방송 뒤 인스타 사과문)과 예고에만 있던 장면은 여전히 뺐다.
- **검색**: 실명 카드라 `16기 상철` 로 안 걸려서, 같은 인스타 계정을 가진 카드끼리 서로의 이름을 검색어로 나눠 갖게 했다(whosthat #150). 같은 날 사람·출연을 나눈 뒤로는 계정이 아니라 `personId` 로 잇는다(§15).
- 색인: IndexNow 가 다음 정시 실행에 보낸다.

## 15. 출연자를 사람과 출연으로 나눴다 (2026-11-13)

계약결혼을 넣다 보니 같은 사람의 계정·확인 근거를 프로그램마다 따로 적고 있었다 — 16기 상철이 다시 공개되고 32기 영수가 비공개로 바뀐 걸 두 줄씩 손으로 고쳤다. 사용자가 "한 번 바꾸면 다 바뀌어야 한다" 고 해서 나눴다(nukko-admin-api #61, nukko-admin #11, whosthat #154).

- **`people`** — 실명·성별·사진·인스타 계정·확인 날짜·근거. **`cast_members`** — 방송 이름·당시 직업·나이·순서 + `person_id`. found/private 검증 제약은 people 로 옮겼다. 사람을 고치면 트리거가 그 사람이 나온 기수들의 `updated_at`(sitemap lastmod)을 올린다.
- **묶는 기준**: 인스타 핸들이 같거나, 나솔사계 `16기 상철` 이름이 나는 솔로 그 기수의 그 이름을 가리키면 같은 사람. 655행 → 543명(두 번 이상 99명). 확인 날짜는 가장 최근 값, 근거 문장은 출연별로 다 남겼다(`[나는 솔로 16기 상철] … / [계약결혼 시즌 1 강정환] …`).
- **합치며 바뀐 값**: 8기 옥순은 `ayo_a0` 가 다른 사람 계정이라 `searching`. 나솔사계에만 있던 실명 3명(26기 순자·24기 영식·27기 영철)이 나는 솔로 카드에도 나온다.
- **이관 동안 출연 갱신 트리거를 껐다** — 안 끄면 전 기수의 lastmod 가 바뀌어 IndexNow 가 모든 주소를 다시 보낸다. 운영 DB 를 복사한 로컬 Postgres(16, `schema.sql` + 데이터 복사)에서 리허설해 기수 `updated_at` 이 그대로인 것까지 확인했다. 로컬 pg_dump 16 은 운영(17)을 못 떠서 asyncpg 로 표를 복사했다.
- **운영 DB 이관과 OCI 배포는 사용자가 터미널에서 직접 돌렸다** — Claude Code 의 자동 권한 판정이 운영 DB 구조 변경·ssh 배포를 막았다. 일반 터미널에서는 `!` 를 붙이지 않는다(zsh 에서 다른 뜻이다).
- 관리자 출연자 추가 창에 "이미 나온 사람인가요?"(`16기 상철`·실명·핸들로 검색), 출연자 줄 위에 같은 사람의 다른 출연을 적는다.


## 16. Vercel 배포 저장 용량 초과 (2026-11-13)

Hobby 한도(Deployment Storage 10GB)를 넘었다 — 10.44GB. 11-11 부터 사흘 사이에 5GB 에서 10GB 로 뛰었다.

- **원인은 파일 크기가 아니라 배포 개수다.** `public/` 은 8KB 다. Vercel 은 배포를 하나하나 통째로 보관하는데 보관 기간이 네 종류 모두 기본값 30일이었다. 누꼬는 브랜치·`dev` push 마다 Preview, `main` 머지와 관리자 "사이트에 반영"(Deploy Hook)마다 Production 이 한 벌씩 생긴다 — 이날 두 시간에만 14개(Production 5·Preview 9). 나솔사계·계약결혼·모비온 작업이 몰린 11-11~13 에 급증했다.
- **고친 것**: 프로젝트 Settings → Security 맨 아래 **Deployment Retention Policy**(메뉴에 바로 안 보이면 같은 화면의 "Recently Deleted Deployments" 설명에 있는 "defined retention policy" 링크로 간다). Canceled 1일, Errored·Pre-Production·Production 1주. 현재 Production(도메인이 걸린 배포)은 기간과 상관없이 안 지워진다.
- **이미 쌓인 것을 `vercel rm whosthat --safe` 로 지우지는 않았다.** 정책이 기존 배포에도 적용되고, `--safe` 는 도메인이 걸린 하나만 남겨 롤백 대상까지 지운다. 지운 배포는 30일 동안 휴지통(Recently Deleted)에 남는데 그게 용량에 잡히는지는 확인하지 못했다.
- 같은 화면에서 CDN Requests 가 865K / 1M 이었다 — 방문자 트래픽이라 배포를 지워도 안 준다.
- **2026-11-19 확인: 둘 다 내려갔다**(사용자 보고). 보관 기간을 줄인 것만으로 Deployment Storage 가 한도 아래로 돌아왔고, CDN Requests 도 줄었다. 휴지통을 따로 비울 일은 없었다.

**네이버와 갈리는 이유.** 네이버는 문서 단위로 검색어에 맞는 한국어 페이지를 올려 주고(색인 49, 거의 한국어), 구글은 도메인 나이·외부 링크 같은 사이트 단위 신뢰를 크게 본다. 네이버 블로그·인스타그램·스레드에 건 링크는 구글 링크 보고서에 하나도 잡히지 않았다 — 구글이 네이버 블로그를 거의 크롤링하지 않고, 인스타·스레드 링크는 중계 주소를 거치는 `nofollow` 라 추천으로 세지 않는다. 사람을 데려오는 효과는 그대로다.

**처음에 "낮은 품질 판정" 이라고 단정했다가 철회했다.** 사용자가 "네이버는 잘 뜨고 더 허술한 사이트도 뜬다" 고 짚었다 — 구글은 절대 품질로 줄 세우지 않고, 오래되고 링크가 많은 사이트는 허술해도 버틴다. 같은 이유로 영어·일본어 기수 페이지 `noindex` 안(sitemap 198 중 132 가 소개 문단 없는 목록, 30일 구글 유입 3명)도 보류했다.

### 18-1. 더 판 것 (같은 날)

**읽은 것.** 언어를 가리지 않고 사이트 전체가 약 90% 내려갔고, 삭제가 아니라 순위 강등이다. 날짜가 맞는 설명이 둘이고 **지금은 둘을 가를 방법이 없다** — 구글은 어느 쪽인지 알려 주지 않는다.

1. **9월 스팸 업데이트에 걸렸다.** 근거는 날짜가 겹친다는 것 하나다. 닮은 패턴을 꼽자면 같은 틀의 페이지가 3언어로 198개(영어·일본어 132개는 이름과 핸들 목록), 업데이트 이틀 전(9/21~22) 같은 문장 틀의 소개 문단 114개가 한꺼번에 들어간 것, 만료 도메인에 전혀 다른 내용을 올린 모양이다. 전부 추측이다.
2. **새 도메인의 초기 노출이 끝났다.** 구글은 새 사이트를 처음 몇 주 높게 노출해 보다가 내리는 경우가 흔하다고 알려져 있다(구글이 공식 인정한 건 아니다). 10/3 은 도메인 등록 6주 뒤다.

**`noindex` 안은 한 번 다시 권했다가 같은 날 도로 보류했다.** 스팸 쪽으로 기울었다고 보고 영어·일본어 기수 페이지 `noindex` 를 권했는데, 하락 전 영어 페이지가 평균 순위 6.6 으로 한국어(10.3)보다 좋았다 — "영어 페이지가 원인" 이라는 추측과 안 맞고, 2번이 맞다면 손해만 본다.

**바로 푸는 길은 없다.** 재검토 요청은 직접 조치에만 있고, 자동 판정은 고친 뒤 구글이 몇 달에 걸쳐 다시 평가해야 바뀐다(구글 공식 설명). 오판(false positive)이 되돌려진 사례는 보고돼 있지만 사이트 주인이 뭘 해서가 아니라 구글이 판정을 고친 경우이고, 며칠 안에 풀렸다고 검증된 사례는 못 찾았다. 사람에게 닿는 유일한 창구는 Google 검색 센터 도움말 커뮤니티(`support.google.com/webmasters/community`)다 — 제품 전문가가 사이트를 보고 원인을 짚고, 오판으로 보이면 구글에 전달한다.

**커뮤니티 질문.** 제목 `직접 조치 없이 10월 3일 하루 만에 검색 노출이 90% 줄었습니다 (nukko.net)`, 카테고리 "크롤링, 색인 생성 및 순위 지정". 본문은 위 표의 사실(등록일·전후 실적·직접 조치와 보안 문제 없음·브랜드 검색 미노출·스팸 업데이트 기간)과 "스팸 정책에 어긋나는 부분인지 새 도메인이라 생기는 일인지 봐 달라" 는 물음이다. Claude in Chrome 확장으로 `support.google.com` 은 열리고 양식도 채워진다(`search.google.com` 과 다르다). 마지막 "게시" 단계는 reCAPTCHA 가 걸려 있어 사람이 누른다. 2026-11-17 에 게시했다 — `support.google.com/webmasters/thread/477969556`. 확장이 다른 노트북의 Chrome 에 붙어 있으면 이 노트북 Chrome 에 창을 하나 띄운 뒤(창이 없으면 확장이 연결 목록에 안 뜬다) 브라우저 전환을 요청한다.

**Search Console 을 보는 법.** Claude in Chrome 확장은 `search.google.com` 을 막고(이동시켜도 새 탭으로 돌아온다), chrome-devtools·Playwright 창은 자동화 브라우저라 구글이 로그인을 막는다. 평소 Chrome 에 `open -a "Google Chrome" <주소>` 로 열고, 앞에 뜬 Chrome 창 하나만 `screencapture -l <창 번호>` 로 찍어 읽었다(창 번호는 CoreGraphics 창 목록에서 뽑는다 — 화면 전체를 찍으면 다른 앱이 함께 찍힌다). 뒤에 깔린 창은 Chrome 이 그리지 않아 빈 화면이 나오므로 앞으로 띄운 뒤 찍어야 한다. URL 검사(`/search-console/inspect?…&id=`)는 주소로 열면 404 라 이 방법으로 못 봤다.

## 19. 머무는 시간·재방문 — 출신 줄 링크·최종 커플 모음·홈 두 단·회차 글 (2026-11-17)

**왜.** 인스타를 찾으면 바로 인스타로 나가는 사이트라, 잘 될수록 방문이 짧다. 기수 상세에서 사이트 안으로 가는 링크가 뒤로가기 하나뿐이었다. 붙잡는 게 아니라 찾은 뒤 한 번 더 누를 곳과 다음 주에 다시 올 이유를 만들기로 했다.

**읽은 것.**

- **보지 않은 UI 를 `main` 에 보내지 않는다.** 반려된 두 판과 칩 띠를 연달아 머지했다. 그 뒤로는 dev 서버에서 사용자가 본 다음 머지했다.
- **혼자 서는 판은 어떤 모양이든 얹어 놓은 것처럼 보인다.** 홈의 모음 진입점이 그랬고, 옆에 받쳐 주는 판(최근 방송)이 생기고서야 자리를 잡았다.
- **"페이지만 먼저" 는 사용자가 바란 것이 아니었다.** 회차 글은 주소가 아니라 글의 풍부함이 요청의 중심이었다.
- **dev 서버가 `src/app/[lang]/` 아래의 새 경로와 새 클래스를 못 볼 때가 있다** — 재시작하면 풀린다.

**배포 뒤 확인.** #188 이 나간 뒤 실제 사이트에서 `/ko/couples`·회차 글(`/ko/i-am-solo/seasons/s34/episodes/2026-11-11`)이 열리고, 다시 쓴 글의 소제목이 나오며 `## ` 가 글자로 새지 않는 것을 봤다. **"사이트에 반영" 은 누를 필요가 없었다** — 빌드가 DB 를 읽으므로, 코드 배포가 DB 에 먼저 넣어 둔 새 글을 함께 구웠다. 코드와 글을 같이 내보낼 때는 DB 를 먼저 채우고 코드를 머지하면 반영 한 번이 준다.

**확인하지 않은 것.** 영어·일본어 화면과 라이트 모드의 새 화면들.

## 20. 숙소와 게임 모음 (2026-11-18)

사용자 아이디어 — "나는 솔로를 따라 해 보려는 사람을 위해 기수별 숙소 주소·이름과 게임·데이트 선택 방식을 모으자". `/ko/solonara` 로 만들었다.

**숙소 조사.** 블로그 두 곳(itshowke·infos2)이 1~15기를 똑같은 표로 싣고 있었다 — 서로 베낀 것이라 독립 확인으로 치지 않았다. 업체 검색광고("나는솔로 8기 촬영지")·리조트 현수막(22·27기)·기사(13·16·21·24기)·투숙 후기로 교차했다. 같은 숙소를 다시 쓴 기수가 있다(4·31기 태안 리트리트 리조트, 9·33기 무주 리틀프로방스). **솔로딕(solodic.co.kr/locations)이 1~34기 숙소를 이미 싣고 있어서** 숙소 목록만으로는 차별점이 아니라고 보고, 놀이의 진행 방법을 이 화면의 몫으로 잡았다. 처음에 "공개된 곳만" 싣자고 했다가 "방송에 나온 것 자체가 공개다" 로 반려됐다 — 남는 위험은 공개 여부가 아니라 **장소를 잘못 짚는 것**이다.

**놀이 데이터.** 회차 글(`season_episodes.json`)에서 선택 장면 문장을 뽑고, 빠진 규칙은 기사·관전노트(33·34기 회차 정리)로 채웠다. 처음 쓴 설명 중 몇 개는 출처에 없는 규칙을 짐작으로 채운 것이라(“가장 호응을 받은 사람”, “가림막 뒤에서”) 확인된 만큼만 남기도록 고쳤다. 34기가 비어 있던 건 회차 글이 방식을 안 적었기 때문이다 — 관전노트에 회차별 방식이 다 있었다.

**화면이 반려된 순서.**
1. 방식 한 줄 + 끝에 회차 글 날짜 링크 — "게임 옆에 링크는 왜 거냐, 무슨 게임인지 설명도 없다". 링크를 빼고 놀이마다 이름 · 진행 방법 · 방송에서는 세 줄로 바꿨다.
2. 흑백 목록 — "놀려는 사람들 페이지인데 딱딱하다". 놀이 하나가 카드 한 장이 되고, 누가 고르는지 칩(남자 파랑·여자 분홍 — 회차 글의 색), 종류 제목에 그림과 형광펜, 숙소는 점선 카드, 위에 놀이 종류 칩을 뒀다.
3. 단(column)으로 쌓은 판 — 34기 옆에 18기가 와서 반려. 줄 순서 격자로 되돌렸다.
4. 종류 칩을 뺐다가 바로 되돌렸다(사용자 결정).
5. 판 키가 달라 생기는 여백 — 세 안(순서 지키는 쌓기·접기·한 줄에 기수 하나) 중 접기를 골랐고, 판마다 놀이 셋 → 하나만 펼치게 줄였다.

## 47. 시청자 투표 (2026-11-22)

사용자 제안 — 회차마다 시청자가 마음에 든 출연자를 뽑고, 최종 선택과 비교해 보는 재미로 매주 다시 오게 하자. 연말 "올해의 인기남·인기녀" 월드컵은 올해는 하지 않기로 했다.

- **저장은 OCI API(사용자 결정).** Vercel 함수 + DB 안은 팀 예산 $1 에 걸려 트래픽이 몰리면 keywi 까지 함께 503 이 될 수 있어 접었다. 정적 페이지는 그대로 두고 투표 상자만 브라우저에서 `api.nukko.net/votes` 를 부른다.
- **결과는 전원 공개(사용자 결정).** 꼴찌·0표를 숨기자는 제안(일반인 출연자에게 상처·악플 재료)을 사용자가 "다 보여 줄 거야" 로 정했다.
- **성별을 묻지 않는다.** "여자면 남자 쪽에 투표" 를 성별 입력 없이 솔로남·솔로녀 각 한 표로 풀었다 — 성별을 받으면 개인정보를 받는 셈이다.
- 회차는 id 가 아니라 (프로그램, 기수, 방송일)로 가리킨다 — 백업 복구 때 id 가 바뀐다. 방송일을 고치면 on update cascade 가 표를 따라 옮긴다(임시 Postgres 에서 확인).
- **같은 날 자리를 옮겼다.** 회차 글 맨 아래 상자를 사용자가 "위치가 마음에 안 든다" 로 반려해 전용 화면 `/ko/vote` 로 뺐다. 헤더 카테고리(상단 바에 모음 화면을 건 안은 이미 반려), 프로그램 화면 탭·사이드바(한 단계 더 들어가야 하고 데스크톱 오른쪽 칸은 배너 자리)를 비교해 추천했고 사용자가 골랐다. 화면은 진행 중인 투표 + 회차별 결과(1위 vs 최종 선택)이고, API 에 프로그램 단위 결과(`GET /votes/{program}`)를 더했다.
- **어떻게 알게 하나**(같은 날): 방문자는 네이버에서 기수 화면·회차 글로 바로 들어와 홈을 거의 안 거친다. 사용자가 고른 둘을 먼저 했다 — 방영 중 기수 화면 머리글과 투표가 열린 회차 글 제목 아래에 칩(현재 1위 포함). 남은 안: 홈 포스터의 방영 중 줄에 투표 표시, 블로그 글 끝 링크와 지난주 1위, 투표 뒤 공유 버튼.
- 확인: 임시 Postgres 에 운영 `/programs` 모양을 넣고 로컬 API + `pnpm dev` 로 34기 11/18 회차에서 찍기 → 순위 → 새로고침 뒤 "내 선택" 유지, 11/11(닫힘·0표)은 상자 없음을 봤다. API 는 중복 표 무시·닫힌 회차 403·다른 기수 출연자 422·IP 상한 429·CORS 를 확인했다.
- **배포(같은 날 밤)** — 순서는 운영 DB 표 → API → 사이트였다.
  - `episode_votes` 는 로컬에 운영 `.env` 가 없어서 OCI 서버의 venv 와 `.env` 로 `schema.sql` 의 투표 절만 실행했다.
  - **API 재시작에서 운영 API 가 약 2분 502 였다.** OCI 의 Python 이 3.9 인데 `_ip_hash` 의 반환 타입을 `str | None`(3.10+)으로 적어 앱이 import 에서 죽었다. 로컬 검증은 3.12 라 못 잡았다. 직전 커밋(`3a0beda`)으로 되돌려 살리고, `Optional[str]` 로 고친 #72 를 3.9 venv 와 서버에서 `import app.main` 이 되는 걸 본 뒤 올렸다. 사이트는 정적이라 그동안에도 떠 있었다(관리자 화면만 멈췄다). 그 뒤로 재시작 전 import 확인이 배포 절차에 들어갔다(`CLAUDE.md`, nukko-admin-api README).
  - nginx 는 이미 `X-Forwarded-For $proxy_add_x_forwarded_for` 를 넘기고 있어 IP 상한이 실제 접속 IP 로 걸린다.
  - 사이트는 #223(→ dev)·#224(→ main). 운영에서 `/ko/vote`(noindex, sitemap 없음)·34기 화면 칩·`/en/vote` 404·콘솔 에러 0 을 봤다. 운영에는 시험 표를 넣지 않았다.
- **느리다는 지적과 속도 개선(같은 날 밤)** — 사용자가 써 보니 투표함이 늦게 뜨고 투표 반영도 오래 걸렸다. 재 보니 브라우저 → OCI 는 0.01초인데 **OCI → Supabase 한 번 왕복이 0.15초**(DB 가 뭄바이 `ap-south-1`, 같은 서버에서 서울 리전은 0.005초)였고, asyncpg 가 질의 하나에 두 번 오가 0.29초, 현황은 4~5번(1~1.5초)·한 표는 8~9번(2~3초) 오갔다. DB 일 자체는 0.0002초였다.
  - API(nukko-admin-api #74): 요청마다 SQL 한 문장 + pre_ping·BEGIN·COMMIT 없는 전용 autocommit 연결. 운영 측정 현황 1~1.5초 → **0.17초**, 한 표 2~3초 → **0.17초**(표를 넣지 않는 잘못된 후보로 잼).
  - 사이트: 투표함을 페이지 HTML 에 바로 그리고(마감은 방송일로 셈) 표 수만 나중에 채운다. 투표는 누르는 순간 "내 선택"(로컬 측정 0.03초), 저장 실패면 되돌리고 안내. API 를 일부러 2초 늦춘 시험과 POST 500 시험으로 확인했다.
  - **Supabase 는 지역을 바꿀 수 없어 서울로 옮기려면 새 프로젝트로 이사해야 한다.** 무료 한도(활성 2개)가 nukko(뭄바이)·keywi-db(us-east-1)로 이미 차 있어(2026-11-22 대시보드 확인) 지금은 새 프로젝트를 못 만든다 — Pro 로 잠깐 올리거나 keywi-db 를 멈춰야 한다. 사용자 결정 전이라 미뤘다. 생성 때 지역을 고른 기록은 없다.
