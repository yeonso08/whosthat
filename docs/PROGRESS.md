## 개편 — 인스타 모음에서 출연자 기록 아카이브로 (2026-10-28 결정)

애드센스 3차 거절 뒤 사용자가 정했다. **기수 상세의 주된 내용이 남의 사이트로 가는 링크라서 "링크 모음" 으로 분류된다** — 가명 21개가 38개 기수 페이지에 똑같이 나오고, 기수마다 다른 값은 나이·직업·핸들 정도다. 글을 늘리는 건 이미 해 봤고(9월 99 → 197단어) 사유가 안 바뀌었다. 그래서 분량이 아니라 **페이지의 주인공을 바꾼다** — 인스타는 여러 칸 중 하나가 되고, 누꼬가 정리한 구조화된 사실이 주인공이 된다. 들어오자마자 인스타를 찾는 목적은 그대로다.

- **산문을 지어 쓰지 않는다**(사용자가 분명히 싫다고 했다). IMDb·축구 기록 사이트처럼 같은 양식에 **페이지마다 다른 사실이 많이** 담기게 하는 쪽이다. 같은 양식 자체는 문제가 아니다 — 문제는 양식에 담긴 값이 페이지마다 거의 같은 것이다.
- **통과는 장담 못 한다.** 구글이 "사람이 쓴 글이 없다" 자체를 문제 삼는 거라면 이걸로도 안 된다. 다만 선택 기록은 승인과 상관없이 방문자에게 쓸모가 있어서 남는다.

순서:

1. **기수마다 선택 기록 (핵심)** — 첫인상 선택, 데이트 선택(라운드별 누가 누구를), 최종 선택을 표와 관계도로. 예: `영수 → 첫인상 영숙 / 1차 데이트 옥순 / 최종 옥순 (커플)`. "나는솔로 N기 데이트 선택 정리" 는 블로그들이 손으로 표를 만들어 올릴 만큼 검색이 있는 말이다. 방송에 나온 사실이라 지어 쓰는 글이 아니다. **나는 솔로 최근 기수 몇 개로 먼저 시안을 만든다** — DB 표·관리자 입력 화면·기수 상세의 기록 화면이 필요하고, 데이터는 직업·나이 때처럼 기사·블로그로 교차 확인한다. 노동이 크다(38기 × 14명 × 여러 라운드).
2. **데이터로 만드는 모음 화면** — 1 이 쌓이면 손으로 안 써도 나오는 화면들: 결혼·커플 모음(프로그램 통합), 특집별 커플 성사율, 출연자 직업·나이 분포, 첫인상 선택이 최종 커플로 이어진 비율. 다른 곳에 없는 정리라 원본 콘텐츠로 가장 확실하게 인정받는 유형이다.
3. **프로그램 늘리기** — 환승연애·하트시그널·돌싱글즈·커플팰리스·연애남매 등. "특정 프로그램 팬 페이지" 에서 장르 아카이브가 된다. 구조는 이미 프로그램을 더할 수 있어 코드 부담이 적고 일은 대부분 데이터 조사다(절차는 `src/data/README.md` 의 "프로그램을 추가할 때"). 1 과 별개로 하나씩 한다.
4. **출연자 사진**(선택) — 아래 "해야 할 일" 9 와 같은 일이다. 이미지 0장인 상태를 벗어나고 시안 D 가 원래 모양이 된다. 삭제 요청 부담이 는다.
5. 어느 정도 쌓이면 **애드센스 4차**.
